# Cancelamento durável H1b — corte V10

Estado: candidato V10 implementado no núcleo protegido, pendente de revisão independente e integração; sem rota HTTP, reader, cursor ou declaração de READY. Base auditada: Metadata `52f2ae1bc97e906cc50c678a1ae84270840293e8` (V9). Consumidor concreto conhecido: `EventosFolhaApprovalProposalService.capture()` no Quickstart apenas persiste proposta/avaliação; a confirmação/cancelamento HTTP ainda não existe. O host futuro valida autenticação e grant atual, constrói `BulkFingerprintContext` confiável e chama o kernel; o Metadata nunca aceita tenant/status do body.

Classificação da mudança: `contrato-publico` (método Java protegido público e `BulkUnitReasonCode`), `arquitetural` (transições e locks duráveis) e `transversal` (DDL, migrator, docs e consumidor futuro). Inventário de aderência: `BulkExecutionStatus` já declara `CANCEL_REQUESTED`/`CANCELLED`, porém não há materialização (`ja-suportado-mal-nomeado-ou-mal-materializado`); reserva, epoch, receipt/admission atômicos, replay antes dos gates e recovery sem callback existem (`suportado-parcialmente`); `cancel_requested_at`, comando idempotente, fence físico entre versões, razão terminal e tombstone distinguível são `lacuna-real-de-contrato`. Não criar registry, DTO público paralelo ou endpoint para aparentar execução.

Mapa de impacto: `JdbcBulkDurableExecution`, `BulkExecutionSnapshot`, `BulkUnitReasonCode`, migration V10 e validação física/ACL em `BulkExecutionMigrator`; `BulkQuotaLedger`, trigger de liberação V5, purge/tombstone V9 e provas PostgreSQL são fluxos afetados. `CHANGELOG`, esta spec e documentação de API do Metadata devem refletir o contrato Java. Quickstart, docs/corpus HTTP do host, Config e Angular ficam para cortes posteriores. Não há release/deploy neste corte.

Constraints e estados: `cancel_requested_at` é nullable, monotônico, gravado uma única vez pelo relógio PostgreSQL; terminal anterior retorna inalterado. `STOPPED+CANCELLED_BY_USER` exige marcador, `next_ordinal < target_count`, tentativa limpa e `terminal_evidence_complete(execution_id,next_ordinal)`; completude de todos os ordinais sempre produz `COMPLETED`/`COMPLETED_WITH_ERRORS`. Marcador não apaga receipt confirmado nem transforma `RECONCILIATION_REQUIRED` em certeza de cancelamento. A tombstone mínima registra `CANCELLED` somente para esse STOPPED; STOPPED histórico permanece STOPPED. Retenção continua 30 dias após terminalização reconciliada; UNKNOWN não é expurgável.

Ordem de locks do cancel/recovery: leitura inicial não bloqueante da identidade; `namespace binding FOR SHARE → operation-control FOR SHARE → deployment bucket FOR UPDATE → subject bucket FOR UPDATE → proposal FOR UPDATE → execution FOR UPDATE → receipt/admission`, com revalidação de escopo/identidade/epoch após locks. O helper de lifecycle não exige READY, inclusive quando control está SUSPENDED. `BulkQuotaLedger.lockProposal` exige READY, portanto o caminho V10 usa o helper próprio; `recover` foi reordenado para essa mesma ordem, evitando inversão com cancel/retention. Transição terminal libera allocation via trigger V5 na mesma transação; ausência de receipt antes de conseguir o lock não prova rollback. Nenhum alvo de domínio é bloqueado pelo cancel.

Transições: replay de receipt/admission é examinado antes do gate do marcador. Se cancel ganha entre prepare e apply, callback novo não roda. Se domínio ganhou, cancel espera seu lock e reconcilia efeito e receipt. ACK de receipt preexistente permanece permitido após marker: se era último ordinal, conclusão normal vence; se há sufixo sem efeito, V10 pode terminalizar cancel após avanço do prefixo. Recovery incrementa epoch e não chama domínio. Efeito incerto/evidência inválida fica `RECONCILIATION_REQUIRED`; não retentar callback nem alegar CANCELLED. `CANCELLED_BY_USER` é reservado ao lifecycle durável e não pode ser emitido por `BulkUnitAdmission.stop`. Fence V10 impede writer V9 de abrir `UNIT_IN_FLIGHT` depois do marker e de inserir evidência posterior a ele, fazendo rollback do callback na transação domínio+receipt; permite ACK da evidência confirmada antes do marker, mas não nova unidade.

Provas PostgreSQL do candidato: `BulkDurableExecutionPostgresTest` cobre pedido anterior à unidade, idempotência e escopo, prefixo confirmado com controle suspenso, cancelamento durante commit e rollback de callback, timeout sem falso aceite, receipt pendente e último ordinal, admission negada, JPA, writer antigo bloqueado pelo guard físico com domínio e receipt revertidos, recuperação sem callback, allocation liberada e tombstone `CANCELLED` com replay impedido. Duas provas determinísticas pausam o commit físico antes da liberação dos locks para demonstrar ambos os vencedores da corrida cancelamento versus recuperação: o vencedor fixa razão/epoch, o perdedor observa o terminal, a allocation é liberada uma vez e nenhum callback ocorre. `BulkDurableMigrationPostgresTest` cobre upgrade por owner não-superuser, drift de ACL/trigger/CHECK/owner e os caminhos de upgrade históricos. As provas de concorrência executam conexões reais separadas; a garantia transacional só vale para domínio e receipt no mesmo manager/connection local. Revisão por outro agente antes de commit/PR.
