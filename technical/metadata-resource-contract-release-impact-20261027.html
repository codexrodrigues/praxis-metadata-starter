Required resource-contract phase

The new resource-contracts phase is serial and independent of the existing managed-owner and optional-policies phases. It requires exactly both reviewed classes and all six named JUnit methods in requiredResourceContractCases. The gate rejects a missing/extra class, missing method, skip, failure, duplicate identity, missing raw phase log or missing/duplicate completed-fixture marker. The complete no-database selection remains mandatory; fixture support is never selected as an executable class.

CustomFieldsResourceE2ETest retains all five actual HTTP/JSONB/schema/cache/export and server-owned-value oracles. CompositeIdResourceE2ETest retains its entire CRUD/filter/options/lookup/stats/OpenAPI method, changing only database setup/reset and cleanup from H2 to the remote assigned fixture. Assertions are not weakened.

Each class creates a unique database using template0 and a unique ordinary LOGIN role on the externally reviewed child. The privileged setup owner is not the HTTP identity. Setup verifies PG17, current_user=session_user, non-SUPERUSER and the necessary CREATEDB/CREATEROLE profile. The setup owner owns the isolated schema and grants the ordinary runtime only CONNECT plus schema USAGE/CREATE; Hibernate owns its own tables. Before Hibernate DDL, runtime preflight verifies its exact database, schema OID/owner, PG17, session identity, all privileged role flags denied and zero outgoing memberships. Client TLS is verify-full, default Java trust verification, required channel binding and an actual valid TLS 1.2/1.3 driver socket witness. pg_stat_ssl behind Neon’s proxy is not used as a frontend TLS witness.

The @ResourceContractNeonTest lifecycle lets Spring finish its after-class listeners and DirtiesContext close the cached context; the lower-order cleanup listener then drops its database and role. Every drop rechecks recorded database/schema/role OIDs and ownership. A private append-only journal records intended names and observed OIDs. An unknown CREATE outcome refuses cleanup and emits no PASS: the coordinator must reconcile actual OIDs before retry. Fresh 64-hex runtime passwords are generated into a separate absolute, regular, mode-0600 credentials file; they are never reused from P4 or uploaded. The scanner checks both resource passwords recursively, including failure logs and final bundle custody. A successful initialization preflight and OID cleanup are both required for the success marker; failed initialization can report cleanup CLOSED separately.

Workflow custody includes the resource phase in source proof and signed release: exact source, assignment, separate raw XML/logs, before/after compiled source/test snapshots, resolved dependencies, staged JAR comparison and credential scans. Signing in P4 does not exempt the subsequent resource phase; receipt construction and publication remain blocked until that phase also succeeds on unchanged bytes.
